# 問題集アップデートスキル

`data/questions/*.json`を、Claude Codeの仕様変更に追従して最新かつ正確な状態に
保つためのスキル。対象領域は`data/questions/`配下のファイル一覧から動的に決定する
（領域数・領域一覧をこのスキル内にハードコードしない）。`ls data/questions/*.json`
または同等の方法で都度確認すること。領域が追加・削除されても、このSKILL.mdや
`references/`配下の更新なしに追従できる設計とする。

**このスキルはユーザーが手動で呼び出す。** 3つのモードを持ち、呼び出し時の
引数または対話でモードを確定させる。

## 実行原則（全モード共通）

- **実行主体は常にサブエージェント。** メインセッション（このSKILL.mdを読んでいる
  あなた自身）はモード判定・サブエージェントへのタスク委譲・結果の集約・
  ユーザーへの提示に徹する。Web調査や大量のJSON読み込みを伴う実作業は行わない。
  これは`data/questions/*.json`への書き込み、レポートファイルの保存、
  gitコミットも含む。これらは必ず専用のサブエージェント（1件のみ、対象領域の
  並列サブエージェントとは別）に、承認済み内容または集約済みレポート本文を
  入力として渡し、書き込み・保存・コミットの実行を委譲する。メインセッション
  自身がファイルを直接編集・コミットしない
- **領域単位で並列化する。** `audit`・`stale`モードでは対象領域それぞれに
  独立したサブエージェントを、対象領域数ぶん並列で起動する。1メッセージ内で
  対象領域数と同数のAgent呼び出しを同時に行い、全ての結果を受け取ってから集約する
- **JSONファイルへの書き込みは承認後のみ。** `add`モードで問題案を作成しても、
  ユーザーが個々の問題案を承認するまで`data/questions/*.json`は変更しない。
  `audit`・`stale`はレポート出力のみで、JSON自体は一切変更しない

## モードの判定

呼び出し時の引数や発言から、以下のいずれかのモードを判定する。
不明な場合はユーザーに確認する。

| モード | 目的 | 対象領域指定 |
|---|---|---|
| `add` | 新規問題の追加 | 可能（省略時は全領域） |
| `audit` | 既存問題の監査（構造・偏り・重複・読解・事実照合） | 可能（省略時は全領域） |
| `stale` | Claude Codeの仕様変更による陳腐化検出 | 不可（常に全領域） |

## モード: `add`（新規問題の追加）

### 手順

1. `data/questions/*.json`のファイル一覧から現在の全領域を確認し、対象領域を
   確定する（引数で指定がなければ全領域を対象にする）。引数で領域が指定された
   場合は、その値がファイル一覧に実在するドメイン名と一致するか検証し、
   一致しないものがあればサブエージェントを起動せずユーザーに訂正を求める
2. 対象領域ごとに、以下を指示するサブエージェントを起動する（対象領域数ぶん並列）:
   - `README.md`の「問題の追加・更新時に参照する情報源」セクションを読み、
     `references/sources.md`の手順に従って優先順位の高い情報源から調査する
   - 対象ドメインの既存問題ファイル（`data/questions/<domain>.json`）を読み、
     既出トピックと重複しない新規トピックを見つける
   - `references/json-schema.md`のフィールド定義に従い、問題案
     （`id`は仮採番、`level`, `question`, `choices`, `correctIndex`, `explanation`）を作成する
   - `references/quality-checklist.md`の「構造の妥当性」（必須フィールドの
     存在、`choices`が4要素、`correctIndex`が整数で範囲内、`choices`内の
     重複がないこと）と「出題の偏り」の両観点で自己チェックし、
     違反があれば作成時点で修正する
   - 問題案を、根拠となる情報源URLとともにサブエージェントの回答として返す
3. 対象領域が2つ以上の場合、ドメイン間の内容重複チェックを専用の1サブエージェントに
   委譲し1回だけ実行する（メインセッションは各領域の問題案を自ら突き合わせない）。
   このサブエージェントには、手順2で集約した全問題案（新規作成分どうし）に加えて
   対象ドメインの`data/questions/<domain>.json`を渡し、以下を検査させる:
   - 新規問題案どうしで、同一の知識点を異なる領域から問うている組み合わせがないか
   - 新規問題案と、対象ドメインの既存問題（他領域を含む）との間で、同一の知識点を
     問うている組み合わせがないか
   - `references/quality-checklist.md`の「重複出題」節の判定基準（意図的な対構成は
     重複としない）に従う
   重複と判定された問題案には、重複相手の`id`または問題案番号とその理由を付けさせる。
   対象領域を1つに絞った実行では、このチェックは行わず後続のレポートにも
   「ドメイン間重複は未検査」と明記する
4. 全サブエージェントの結果（重複チェック結果を含む）を集約し、領域・レベル・
   問題文・選択肢・正解・解説・出典URLに加え、重複が指摘された問題案には
   重複相手と理由を明記したレポート形式でユーザーに提示する。重複と判定された
   問題案は、既定では非推奨（採用しない案）としてユーザーに示すが、最終判断は
   ユーザーに委ねる
5. ユーザーの承認を待つ。承認されなかった問題案は破棄する
6. 承認された問題案を、書き込み専用のサブエージェントに以下を入力として渡し、
   JSON追記を委譲する:
   - 対象ドメインの既存問題ファイル（`data/questions/<domain>.json`）
   - 承認された問題案（`level`, `question`, `choices`, `correctIndex`, `explanation`）
   このサブエージェントは、対象ファイル内の既存最大連番を開始番号として、
   同一領域内で承認順に1件ずつ増分した`id`を確定させる（同一領域の複数承認
   問題に同じ`id`を割り当てない）。確定した`id`とともに`questions`配列へ追記する
7. 同じサブエージェントに`node --test`を実行させ、結果をメインセッションに
   報告させる。メインセッションはその結果をユーザーに提示する

## モード: `audit`（既存問題の監査）

### 手順

1. `data/questions/*.json`のファイル一覧から現在の全領域を確認し、対象領域を
   確定する（引数で指定がなければ全領域を対象にする）。引数で領域が指定された
   場合は、その値がファイル一覧に実在するドメイン名と一致するか検証し、
   一致しないものがあればサブエージェントを起動せずユーザーに訂正を求める
2. 対象領域ごとに、以下を指示するサブエージェントを起動する（対象領域数ぶん並列）:
   - `references/quality-checklist.md`の「構造の妥当性」「出題の偏り」
     「重複出題」「読解チェック」の各観点で、対象ドメインの
     `data/questions/<domain>.json`を検査する。ただし`id`の重複チェックは
     対象ドメイン内のみで行い、「全ドメイン間で重複がない」とは主張しない
     （対象領域を1つに絞った実行では他ドメインのファイルを読まないため、
     ドメイン間重複は原理的に検出できない）
   - 事実照合が必要な問題（コマンド名・フラグ名・JSON構造・数値上限・
     機能の有無等を問う問題）にフラグを立て、`references/sources.md`の
     手順で公式情報源と照合する
   - 検出した指摘それぞれに、深刻度（要修正 / 検討推奨 / 参考情報）・
     何が問題か・なぜ問題か・根拠を付けて返す
3. 対象領域が全領域の場合は、ドメイン間`id`重複チェックを専用の1サブエージェントに
   委譲し1回だけ実行する（メインセッションは全`data/questions/*.json`を自ら
   読み込まない。対象領域ごとの監査サブエージェントが既に各ファイルを読んでいる
   ため、重複読み込みを避けるためにもこのサブエージェントに集約させる）。
   このサブエージェントには重複`id`一覧、またはゼロ件であればその旨のみを
   簡潔に返させ、メインセッションは結果のみを受け取る。
   対象領域を一部に絞った実行では、このチェックは行わずレポートにも
   「ドメイン間重複は未検査」と明記する
4. 全サブエージェントの結果を集約し、深刻度順に並べたレポートを作成する
5. レポート保存専用のサブエージェントに、集約済みレポート本文と実行日を
   入力として渡し、`docs/superpowers/reports/YYYY-MM-DD-question-audit-<対象領域>.md`
   （`YYYY-MM-DD`は実行日、`<対象領域>`は対象ドメイン名をハイフン区切りで
   連結したもの。全領域の場合は`all`）への保存とgitコミットを委譲する。
   同日に異なる対象領域で複数回実行しても、ファイル名が対象領域ごとに
   分かれるため既存レポートを上書きしない。同一対象領域を同日に複数回
   実行する場合は、ファイル名に実行時刻（`HHmm`）を付加
   （`YYYY-MM-DD-question-audit-<対象領域>-HHmm.md`）して上書きを避ける
6. 検出ゼロの領域があっても、その旨と検査範囲をレポートに明記する

### このモードでは行わないこと

- `data/questions/*.json`の修正（指摘一覧の提示のみ）
- 指摘への対応要否の判断（ユーザーが個別に判断する）

## モード: `stale`（陳腐化した問題の検出）

### 手順

1. `data/questions/*.json`のファイル一覧から現在の全領域を確認する
   （対象領域は常に全領域。領域指定は受け付けない）
2. 対象領域それぞれに、以下を指示するサブエージェントを起動する
   （対象領域数ぶん並列）:
   - `README.md`の「問題の追加・更新時に参照する情報源」セクションを
     上から順に読み、`references/sources.md`の手順で公式情報源を通読する
   - `references/quality-checklist.md`の「事実照合」観点のみを使い、
     対象ドメインの全問題が現行のClaude Code仕様と矛盾していないか照合する
     （コマンド名・フラグ名・JSON構造・数値上限・機能の廃止/統合/改名・
     問題が前提とする挙動の陳腐化）
   - 「出題の偏り」「重複出題」「読解チェック」等のスタイル面の観点は
     `audit`モードの担当であり、`stale`では検査しない
   - 検出した指摘それぞれに、何が古くなったか・現行の正しい仕様・根拠URLを付けて返す
3. 全サブエージェントの結果を集約する
4. レポート保存専用のサブエージェントに、集約済みレポート本文と実行日時を
   入力として渡し、`docs/superpowers/reports/YYYY-MM-DD-question-staleness.md`
   （`YYYY-MM-DD`は実行日）への保存とgitコミットを委譲する。同日に既に
   同名のレポートが存在する場合は、ファイル名に実行時刻（`HHmm`）を付加
   （`YYYY-MM-DD-question-staleness-HHmm.md`）して上書きを避ける
5. 指摘ゼロの場合も、チェックした情報源と範囲を明記してレポートを作成する

### このモードでは行わないこと

- `data/questions/*.json`の修正（指摘一覧の提示のみ）
