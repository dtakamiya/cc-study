# 問題集アップデートスキル 設計

作成日: 2026-08-05

## 目的

`data/questions/*.json`（5領域・全229問）を、Claude Codeの仕様変更に追従して最新かつ正確な
状態に保つための、ユーザーが手動で呼び出す再利用可能なスキルを作成する。

これまでは「問題データ健全性チェック」（2026-08-02）のような一過性の監査タスクを都度ゼロから
設計・実行していた。同じ観点・同じ情報源を毎回テキストで説明し直すのは非効率であり、
呼び出すたびに手順がぶれるおそれもある。スキル化することで、手順・情報源・チェック観点を
1箇所に固定し、`Skill(question-bank-update, ...)` の呼び出しだけで再現できるようにする。

## スコープ

対象は `data/questions/*.json` の5ファイル・全229問と、それを追加・監査するための
`.claude/skills/question-bank-update/` 一式。

このスキルが担う3つのモード:

1. **新規問題の追加 (`add`)** — 公式情報源を調査し、既存問題と重複しない新規トピックの
   問題案を作成してユーザーに提示、承認後にJSONへ追記する
2. **既存問題の監査 (`audit`)** — 2026-08-02のレポートと同じ観点（構造・出題の偏り・
   重複・読解性・事実照合）で指摘一覧を作成する。修正提案のみを行い、
   JSONへの直接修正はこのスキルの範囲外
3. **陳腐化した問題の検出 (`stale`)** — 公式情報源を通読し、Claude Codeの仕様変更によって
   内容が現行仕様と矛盾した問題を洗い出す。指摘のみで修正はしない

`js/`（アプリケーションコード）や`tests/`の変更はこのスキルのスコープ外。

## 全体構成

```
.claude/skills/question-bank-update/
  SKILL.md                 # モード分岐・サブエージェント委譲手順・完了条件
  references/
    sources.md              # 情報源の参照方法（README.mdの該当セクションへの誘導。内容は複製しない）
    quality-checklist.md    # 妥当性チェック観点の実体（README由来＋2026-08-02監査の手法を集約）
    json-schema.md          # 問題JSONのフィールド定義・id命名規約
```

情報源一覧（Claude Code Docs / Engineering Blog / Academy等）はREADMEに既に一次情報として
存在する。スキル側に複製すると、README更新時にスキルが追従できず陳腐化するため、
`sources.md`は「READMEの『問題の追加・更新時に参照する情報源』節を読め」という薄い誘導に
とどめる。一方、JSON構造やチェック観点の詳細な検出ロジックはREADMEに書かれていない
実装知識なので、`references/`側に実体を持たせる。

## 共通方針

- **実行主体は常にサブエージェント。** メインセッションはモード判定・サブエージェントへの
  タスク委譲・結果の集約・ユーザーへの提示に徹する（オーケストレーション）。
  CLAUDE.mdの「メインセッションで作業をせずオーケストレーションに徹せよ」に従う。
- **領域単位の並列化。** `audit`・`stale`モードは5領域（basic-operations / feature-usage /
  prompt-design / security-permissions / token-efficiency）を独立したサブエージェントに
  最大5並列で割り当てる。領域はデータ的に独立しており、共有状態がないため並列化に適する。
- **Web調査はサブエージェントに委譲。** 公式ドキュメントのWebFetch/WebSearchによる調査は、
  トークン消費が大きくメインセッションの文脈を圧迫するため、常にサブエージェント側で行う。
- **JSON直接編集は承認後のみ。** `add`モードで問題案を書き込む場合も、ユーザーが個々の
  問題案を承認するまでJSONファイルは変更しない。`audit`・`stale`はレポート出力のみで、
  修正自体は別セッション・別依頼として扱う。

## モード1: 新規問題の追加 (`add`)

### 入力
- 対象領域（省略時は5領域全部）
- 任意でトピックの指定（例: 「サブエージェントの並列実行数上限について」）

### 手順
1. 対象領域ごとにサブエージェントを起動（最大5並列）
2. 各サブエージェントは以下を実施:
   - `references/sources.md`経由でREADMEの情報源一覧を確認し、優先順位の高い順
     （Docs → Engineering Blog → Academy → Certification）にWebFetch/WebSearchで調査
   - 対象領域の既存問題（`data/questions/<domain>.json`）を読み、既出トピックとの重複を除外
   - 新規トピックについて、`references/json-schema.md`のフィールド定義に従い問題案を作成
     （`id`は次の連番を仮採番、`question`/`choices`/`correctIndex`/`explanation`を含む）
   - `references/quality-checklist.md`の妥当性チェック観点（正解選択肢の長さ・
     `correctIndex`の偏り・断定表現の多用）を自己チェックし、違反があれば作成時点で修正
3. 各サブエージェントの結果をメインセッションで集約し、レポート形式でユーザーに提示
   （領域・レベル・問題文・選択肢・正解・解説・出典URLを含む）

### ユーザー承認後
- 承認された問題案のみを対象JSONファイルに追記（`id`の最終採番はこの時点で確定）
- `node --test`を実行し、結果をユーザーに報告
- 却下された問題案は破棄し、JSONに反映しない

## モード2: 既存問題の監査 (`audit`)

### 入力
- 対象領域（省略時は5領域全部）

### 手順
1. 対象領域ごとにサブエージェントを起動（最大5並列）
2. 各サブエージェントは`references/quality-checklist.md`に従い、対象領域内で以下を検査:
   - 構造の妥当性（`id`重複・必須フィールド欠落・`choices`要素数・`correctIndex`範囲）
   - 出題の偏り（`correctIndex`分布・正解選択肢の長さ・断定表現）
   - 重複出題（領域内の問題文・解説のテキスト類似）
   - 読解チェック（正解が複数成立、正解が実は誤り、問題文と解説の矛盾、レベル配置の妥当性）
   - 事実照合が必要な問題にフラグを立て、`references/sources.md`経由で公式情報源と照合
3. メインセッションで各領域の結果を集約し、深刻度別（要修正 / 検討推奨 / 参考情報）に
   分類したレポートを`docs/superpowers/reports/YYYY-MM-DD-question-audit.md`に保存し、
   コミットする

### このモードでは行わないこと
- `data/questions/*.json`の修正
- 指摘への対応要否の判断（ユーザーが個別に判断する）

## モード3: 陳腐化した問題の検出 (`stale`)

### 入力
- なし（常に229問全体が対象。領域指定は不可）

### 手順
1. 5領域それぞれにサブエージェントを起動（5並列）
2. 各サブエージェントは`references/sources.md`経由でREADMEの情報源一覧を上から順に
   WebFetch/WebSearchで通読し、以下の観点で対象領域の全問題と照合する:
   - コマンド名・CLIフラグ名・スラッシュコマンド名が現行仕様と一致するか
   - 設定ファイルのJSON構造・キー名が変更されていないか
   - 数値上限（コンテキストウィンドウサイズ等）が変わっていないか
   - 機能が廃止・統合・改名されていないか
   - 問題が前提とする挙動（例: auto modeの二層防御の内容）が最新の説明と矛盾していないか
3. `audit`モードと重複する観点（長さ偏り・断定表現等スタイル面）は対象外とし、
   「事実として古くなった」問題のみに絞る
4. メインセッションで集約し、`docs/superpowers/reports/YYYY-MM-DD-question-staleness.md`に
   保存してコミットする。指摘ゼロの場合も、チェックした情報源と範囲を明記して報告する

### このモードでは行わないこと
- `data/questions/*.json`の修正

## references/ の内容方針

### `sources.md`
README.mdの「問題の追加・更新時に参照する情報源」セクションを直接参照する指示のみを書く。
情報源のURLリストそのものは複製しない（README更新時の追従漏れを防ぐため）。
サブエージェントへの委譲時は「まず`README.md`の当該セクションを読んでから調査を開始せよ」
という指示をSKILL.md側からも明示する。

### `quality-checklist.md`
README.mdの「問題作成時の妥当性チェック観点」（3項目: 正解選択肢の長さ・`correctIndex`偏り・
断定表現）をベースに、2026-08-02監査で実際に使った検出ロジック（構造チェック・読解チェック・
重複検出の具体的な進め方）を追記した実装レベルのチェックリストとして持つ。
これはREADMEに書かれていない実装知識のため、複製ではなく本スキル固有の資産として保持する。

### `json-schema.md`
問題オブジェクトのフィールド定義（`id`, `level`, `question`, `choices`, `correctIndex`,
`explanation`）、レベルの4値、ドメインprefix規約（`basic-` / `feature-` / `prompt-` /
`security-` / `token-`）を記載する。既存JSONファイルの実例から抽出する。

## やらないこと

- 定期実行（cron/loop）との連携。今回はユーザー手動起動のみに絞る
- `js/`（アプリケーションコード）・`tests/`の自動変更
- `audit`・`stale`モードでの自動修正（レポート止まり）
- 5領域以外の新領域追加（既存5領域の枠組みを前提とする）

## 成功基準

- `Skill(question-bank-update, args="add domain=security")`のようにモードと対象領域を
  指定して呼び出せる
- 3モードいずれも、Web調査・大量JSON読み込みを伴う実作業はサブエージェントが行い、
  メインセッションはオーケストレーションに徹している
- `audit`・`stale`モードの成果物は`docs/superpowers/reports/`配下にMarkdownで保存される
- `add`モードはユーザー承認を経てからのみJSONファイルを変更し、承認後は`node --test`が
  実行され結果が報告される
- 情報源リスト・妥当性チェック観点の一次情報はREADME.mdに一本化されたままで、
  スキル側はそれを複製せず参照する
