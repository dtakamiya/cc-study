# 問題データ健全性チェック 設計

作成日: 2026-08-02

## 目的

`data/questions/*.json` の全229問について、問題と解答の正確性を予防的に点検し、
結果をレポートとして提出する。特定の不具合報告に基づくものではなく、健康診断にあたる。

## スコープ

対象は `data/questions/*.json` の5ファイル・全229問。

| ファイル | 問題数 |
|---|---|
| `basic-operations.json` | 47 |
| `feature-usage.json` | 47 |
| `prompt-design.json` | 45 |
| `security-permissions.json` | 45 |
| `token-efficiency.json` | 45 |

**成果物はレポートのみ。** データファイルの修正・コミットは行わない。

## 全体構成

3フェーズで、コストの低い順に段階的に絞り込む。

```
フェーズ1: 機械的チェック（スクリプト・全229問）
      ↓
フェーズ2: 読解チェック（全229問を読む）＋ 事実照合フラグ付け
      ↓
    件数を報告し、照合範囲をユーザーに確認
      ↓
フェーズ3: 事実照合（フラグ付き問題のみ・公式ドキュメント参照）
      ↓
   レポート出力
```

## フェーズ1: 機械的チェック

使い捨てのNodeスクリプトをscratchpadに書いて実行する。
`tests/` への恒久的なテスト追加は今回は行わない（診断が目的のため）。
結果を見て常時チェックしたい項目が判明した場合は、別途検討する。

### 検出項目

**構造の妥当性**

- `id` の重複
- `id` の命名規約違反（`basic-` / `feature-` / `prompt-` / `security-` / `token-` プレフィクス、連番）
- 必須フィールド（`id`, `level`, `question`, `choices`, `correctIndex`, `explanation`）の欠落・空文字
- `choices` の要素数が4でない
- `choices` 内の重複
- `correctIndex` が範囲外
- `level` が既定の4値（`beginner` / `intermediate` / `advanced` / `expert`）以外

**README要件の充足**

- 各領域・各レベルの問題数が10未満でないか

**出題の偏り（READMEの「妥当性チェック観点」に対応）**

- `correctIndex` の分布の偏り（領域×レベル単位で集計）
- 正解選択肢の文字数が他の選択肢より極端に長い/短い問題
- 誤答選択肢に含まれる断定表現（「絶対」「一切」「存在しない」「できません」「必ず」等）の出現

**重複出題**

- 問題文・解説のテキスト類似による同一トピックの重複検出

## フェーズ2: 読解チェック

全229問を読み、機械的検査では検出できない欠陥を探す。

### 検出項目

- 正解が複数成立する問題
- 正解とされる選択肢が実は誤りである問題
- 問題文と解説の矛盾
- 解説が正解の根拠を説明していない
- レベル配置の妥当性（beginner に expert 級の問題が置かれている等）

### 事実照合フラグ

同じ読解の過程で、公式ドキュメントによる裏取りが必要な問題にフラグを立てる。
対象は検証可能な事実を問う問題:

- コマンド名・CLIフラグ名
- スラッシュコマンド名
- 設定ファイルのJSON構造・キー名
- 数値上限（コンテキストウィンドウサイズ等）
- 機能の有無・廃止状況

Claude Code は仕様変更が頻繁なため、記憶のみを根拠に「正しい」と判断しない。

### ユーザー確認ゲート

フェーズ2完了時点でフラグの件数を報告し、フェーズ3でどこまで照合するかをユーザーに確認する。
無制限に WebFetch を積む形にはしない。

## フェーズ3: 事実照合

フラグ付き問題のうち、ユーザーが承認した範囲を公式ドキュメントで検証する。

### 参照する情報源

README「問題の追加・更新時に参照する情報源」の方針に従い、以下の優先順位で参照する。

1. [Claude Code Docs](https://code.claude.com/docs) — 最優先。CLIオプション、スラッシュコマンド、hooks、permission-modes、sandbox、MCP、subagents、skills
2. [Anthropic Engineering Blog](https://www.anthropic.com/engineering) — 設計思想・安全機構の背景
3. [Claude Platform Docs](https://platform.claude.com/docs) — コンテキストウィンドウ、プロンプトキャッシング等

日本語ブログ等の二次情報は根拠として採用しない。

### 照合の粒度

フラグ件数に応じて調整する。数件なら個別に、数十件ならトピック単位でドキュメントを取得し一括照合する。

## 成果物

`docs/2026-08-02-question-audit.md` に Markdown で出力する。

### レポート構成

深刻度順に並べ、以下のセクションに分ける。

1. **事実誤り** — 現在の仕様に照らして解答が誤っている
2. **出題欠陥** — 正解が複数ある、選択肢重複、問題文と解説の矛盾等
3. **偏り・スタイル** — `correctIndex` の偏り、正解選択肢の長さ、断定表現

### 各指摘に含める情報

- 問題ID / 領域 / レベル
- 何が問題か
- なぜ問題か
- 根拠（公式ドキュメントURL、または README の方針への参照）
- 深刻度（要修正 / 検討推奨 / 参考情報）

レポート冒頭に、チェック範囲と検出件数のサマリを置く。

## やらないこと

- `data/questions/*.json` の修正・コミット
- アプリ側コード（`js/`）の変更
- `tests/` への新規テスト追加
- 全229問の公式ドキュメント照合（フェーズ3は絞り込んだ分のみ）
- 問題の新規追加

## 成功基準

- 全229問がフェーズ1・フェーズ2の検査を通過している
- フェーズ3の照合範囲がユーザーの承認を得ている
- レポートの各指摘に根拠が付いている
- 検出ゼロの場合も、その旨と検査範囲を明記したレポートを出す
